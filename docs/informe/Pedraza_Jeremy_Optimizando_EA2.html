def buscar_proyecto(base: Path):
    """Ubica la carpeta del proyecto (raíz del repo o una subcarpeta) con el paquete completo."""
    candidatos = [base, *sorted(p.parent for p in base.glob("*/pyproject.toml"))]
    return next((p for p in candidatos if (p / "src" / "ml_scraper" / "pipeline.py").exists()), None)

def sh(*cmd: str) -> str:
    """Ejecuta un comando en la raíz del repositorio y devuelve su salida."""
    r = subprocess.run(cmd, cwd=RAIZ, capture_output=True, text=True, encoding="utf-8")
    return (r.stdout + r.stderr).strip()

Fase 1. Control de versiones con Git y GitHub¶

El repositorio sigue un GitFlow simplificado: main contiene lo que está en producción (cada commit se despliega), develop integra funcionalidades terminadas y cada funcionalidad se desarrolla en una rama feature/*. Las ramas se fusionan con --no-ff (en GitHub, Create a merge commit de un pull request) para que el historial muestre explícitamente cada integración.

Cada mensaje sigue el patrón tipo(alcance): descripción. La tabla clasifica el historial por tipo para verificar la convención.

import re
import pandas as pd

mensajes = sh("git", "log", "--all", "--no-merges", "--pretty=%s").splitlines()
tipos = [m.group(1) if (m := re.match(r"(\w+)(\(.+?\))?:", s)) else "otro" for s in mensajes]
fusiones = len(sh("git", "log", "--all", "--merges", "--pretty=%h").splitlines())

df_commits = pd.Series(tipos).value_counts().rename_axis("Tipo").reset_index(name="Commits")
print(f"Commits sin fusión: {len(mensajes)} | Fusiones (--no-ff): {fusiones} | "
      f"Cumplen la convención: {sum(t != 'otro' for t in tipos)}/{len(tipos)}")

Fase 2. Pruebas automatizadas¶

La EA1 era un cuaderno: verificar que seguía funcionando exigía ejecutarlo y revisar las salidas a mano. En la EA2 la lógica se trasladó al paquete ml_scraper y se cubrió con 30 pruebas pytest de tres tipos:

  • Unitarias: normalización de precios, extracción defensiva, cálculo de descuentos.
  • Regresión: la conclusión de negocio de la EA1 (+17,05 % sobre el promedio) debe mantenerse.
  • Integración: el pipeline completo genera los CSV, el gráfico y el index.html que se despliega.

Esta es exactamente la orden que ejecuta el workflow CI en cada push y pull request.

Fase 4. Flujo DevOps con GitHub Actions¶

Workflow Disparador Trabajos
ci.yml push a cualquier rama de trabajo y pull request hacia main/develop lint (ruff) → test (matriz 3.10/3.11/3.12, cobertura ≥ 85 %) y scrapy
cd.yml push a main, etiquetas v* o ejecución manual build (pruebas + pipeline) → deploy (GitHub Pages) → smoke (curl al sitio)

for nombre in ("ci.yml", "cd.yml"):
    texto = (RAIZ / ".github" / "workflows" / nombre).read_text(encoding="utf-8")
    trabajos = re.findall(r"^  (\w+):\n    name: (.+)$", texto, flags=re.M)
    print(f"{nombre}")
    for clave, titulo in trabajos:
        dep = re.search(rf"^  {clave}:\n(?:    .+\n)*?    needs: (.+)$", texto, flags=re.M)
        print(f"   - {clave:7} {titulo:42} needs: {dep.group(1) if dep else '—'}")

# Despliegue continuo: cada fusión en main vuelve a probar, ejecuta el pipeline de scraping
# y publica el reporte resultante en GitHub Pages.
# Requisito único: Settings → Pages → Source = "GitHub Actions".
name: CD

on:
  push:
    branches: [main]
    tags: ["v*"]
  workflow_dispatch:
    inputs:
      en_vivo:
        description: "Ejecutar el scraping contra el sitio real (en lugar del snapshot)"
        type: boolean
        default: false

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: false

jobs:
  build:
    name: Probar y construir el reporte
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip
      - name: Instalar
        run: |
          pip install -r requirements-dev.txt
          pip install -e .
      - name: Pruebas (puerta de calidad antes de desplegar)
        run: pytest -q --cov --cov-fail-under=85
      - name: Ejecutar pipeline de scraping
        run: python -m ml_scraper --site site ${{ inputs.en_vivo && '--en-vivo' || '' }}
      - name: Guardar datos extraídos
        uses: actions/upload-artifact@v4
        with:
          name: datos-extraidos
          path: out/
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with:
          path: site

  deploy:
    name: Desplegar en GitHub Pages
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4

  smoke:
    name: Prueba de humo del despliegue
    needs: deploy
    runs-on: ubuntu-latest
    steps:
      - name: Verificar que el sitio responde y contiene el reporte
        run: |
          URL="https://${{ github.repository_owner }}.github.io/${{ github.event.repository.name }}/"
          for i in 1 2 3 4 5; do
            if curl -fsSL "$URL" | grep -q "Galaxy A55"; then echo "OK: $URL"; exit 0; fi
            sleep 15
          done
          echo "El sitio no respondió correctamente: $URL"; exit 1

Fase 5. Resultados y conclusiones¶

Resultados

  1. El código de la EA1 se reorganizó en un paquete de seis módulos (utils, producto, resenas, competencia, analisis, reporte) más un orquestador, y la araña de Scrapy reutiliza la misma lógica de extracción que validan las pruebas.
  2. El historial evidencia el flujo de ramas: cada funcionalidad nació en una rama feature/*, se integró en develop mediante fusión sin avance rápido y la versión se promueve a main mediante pull request.
  3. Las 30 pruebas automatizadas pasan con una cobertura superior al 85 %, y la prueba de regresión confirma que la refactorización no alteró la conclusión de negocio de la EA1: el artículo se ofrece 17,05 % por encima del promedio de su mercado y ocupa el puesto 10 de 12 por precio.
  4. Cada fusión en main vuelve a probar el código, ejecuta el scraping y publica el reporte en GitHub Pages, con una prueba de humo que verifica que el sitio desplegado responde.

Conclusiones

  • Git y GitHub convierten un cuaderno aislado en un activo trazable: cada cambio tiene autor, motivo y revisión, y cualquier versión puede reconstruirse.
  • Las pruebas automatizadas son la condición que hace seguro el despliegue continuo: sin ellas, publicar en cada fusión solo automatizaría la propagación de errores.
  • Separar la lógica de extracción del origen del HTML (snapshot o sitio real) fue la decisión que permitió probar el scraping en CI de forma determinista y sin generar tráfico hacia Mercado Libre.
